## Intended experience

Replace the separate Settings and Accounts text buttons with one gear icon anchored
at the bottom-left of the inbox sidebar. It opens a centered Settings dialog with
module navigation on the left and the selected module content on the right.
The inbox remains visible beneath a dim overlay and stays mounted throughout.

```text
Inbox remains visible behind the overlay
     +---------------------------------------------------+
     | Settings                                      [x] |
     |----------------+----------------------------------|
     | General        | Selected module heading          |
     | Accounts       | Description                      |
     | Search         |                                  |
     | AI and models  | Module controls / account list   |
     | Privacy        | Explicit actions and feedback    |
     +---------------------------------------------------+
 [gear]  Settings entry point in the inbox sidebar footer
```

## Proposed interaction decisions

- Gear button: localized accessible name, hover/focus tooltip, visible focus indicator,
  at least 40px target, and `aria-haspopup="dialog"`. Keep sync status readable nearby.
  When the sidebar is collapsed or hidden on narrow windows, expose the same action
  as a gear icon in the toolbar; show only the applicable entry point.
- Desktop dialog target: approximately 960px maximum width, bounded by viewport
  margins, and up to 85dvh height. Use a roughly 200px module sidebar, fixed header,
  and independent content scrolling. Long account guides must not move the close button.
- Narrow windows: retain dialog behavior, adapt navigation to a compact module selector,
  and use nearly the full viewport with safe margins. Avoid horizontal page overflow.
- Open General initially; remember the last module only within the running session.
  Explicit account-management entry points may open Accounts directly. Close with the
  header button or Escape; outside clicks do not dismiss forms.
- Trap focus inside the dialog, make the background inert, lock background scrolling,
  and restore focus to the opener or its visible replacement. Use existing bits-ui Dialog.
  Suspend window-level inbox triage shortcuts while open; inert alone is insufficient.
  Settings and the command palette must not be open simultaneously.
- Preserve selected message, reader subtree, search text/mode, loaded pages, mailbox
  scope, sidebar expansion, and scroll position across opening/closing. Background sync
  continues and may reconcile messages normally; do not freeze or duplicate subscriptions.
- Save at module/action level, retaining existing explicit AI save, download consent,
  and tokenizer rebuild actions. No global Save button or implicit network operations.
- For unsaved forms, intercept close/module changes and show inline Stay/Discard choices;
  Escape must not bypass this guard. Clear credential inputs when discarding or leaving.
  Do not retain inactive secret-bearing forms just to preserve drafts.
- While an explicit save, download, or rebuild is pending, keep that module visible and
  prevent dismissal/module changes until settled; show progress and errors in place.
  OAuth additionally exposes explicit cancellation after native readiness acknowledgement.
  Reconcile cancellation/completion before leaving; preserve late-ready cancellation handling.
  App teardown retains existing native cleanup; do not invent unsupported cancellation IPC.
- Support EN/PT-BR, both existing themes, shared motion tokens, and reduced motion.

## Initial module order and scope

| Module | Existing functionality to expose |
|---|---|
| General | Language selector; system-managed appearance explanation, without adding a theme preference |
| Accounts | Connected accounts and Add account; reuse authentication methods, presets, help, and cancellation |
| Search | Tokenizer selection/rebuild and experimental semantic projection toggle with honest limitation text |
| AI and models | Optional Ollama/BYOK settings, API-key submission, model cache status and explicitly consented downloads |
| Privacy | Explain local storage and per-message remote-image consent; no global remote-image permission |

Accounts initially shows the connected list and an Add account action. Open the account
form as an internal detail view with Back to accounts, rather than nesting another modal.
Local account photo controls from the mailbox plan belong here when implemented. Account
editing/removal and new sync/privacy settings are outside this addendum's scope.
First-run account setup and locked-vault recovery remain dedicated entry screens.

## Implementation approach and repository evidence

- `DesktopApp.svelte` currently replaces `InboxSession` with either `SettingsView` or
  `OnboardingView`. Keep the established inbox mounted and render Settings as a sibling
  overlay. Account loading/addition must not switch the ready inbox into onboarding.
- Keep one authoritative `AccountController` shared with the Accounts module. Refresh
  account metadata after addition without remounting the inbox or clearing mailbox scope.
  Extract reusable account-list content from `OnboardingView`; reuse `AccountForm` and
  `AccountHelpGuide` without copying their logic or overwriting current local edits.
- Split `SettingsView` content into typed module components under `lib/settings/` and
  introduce a dialog host. Use a typed module-ID union and explicit component composition;
  no plugin registry or new settings persistence layer is needed.
- `InboxSession` currently reads experimental search availability only on mount. Publish
  successful Search module changes to the live inbox controller, using its existing setter
  to reconcile a disabled semantic mode. Do not depend on a close/reopen remount to apply it.
- Keep pending-operation ownership and stale-response guards explicit when extracting
  forms. Credentials stay in transient unbound inputs/invoke arguments and are cleared on
  submission/teardown. They never enter drafts, localStorage, logs, or module metadata.
- Reuse established Tauri commands, vault storage, DTOs, and consent boundaries. This
  presentation change requires no Rust, schema, or core trait changes. Account photo/backend
  work remains governed separately by the existing mailbox plan.

## Falsifiable acceptance criteria for implementation

- One visible gear entry point opens the centered dialog; separate Settings/Accounts text
  buttons are removed. Every existing setting is reachable through the listed modules.
- An inbox mounted once stays mounted through repeated opens, module changes, account
  additions, and closes. Selection/query/scroll remain stable without sync changes; sync
  continues without duplicate connections. Search settings update the live session.
- Keyboard-only tests cover trapped/restored focus, narrow/collapsed-sidebar access,
  Escape/dirty guards, and R/E/Delete/Ctrl-or-Cmd+K causing no background inbox action.
- Account tests cover add success/failure, cancellation before/after readiness, completion
  racing cancellation, and credential cleanup. Initial setup/vault unlock remain functional.
- Deferred-response tests cover pending saves/downloads/rebuilds and teardown; no stale
  result mutates a disposed module. Opening/navigating Settings never downloads or probes.
- Visual QA covers long provider guides, many accounts, long labels, viewport resizing,
  both languages/themes, reduced motion, and loading/error/retry states.
