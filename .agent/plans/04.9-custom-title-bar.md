## Intended experience

Replace the OS title bar with a compact application-owned bar that matches the existing
light/dark surfaces, typography, separators, focus treatment, and motion tokens.
Keep the bar visible across account loading, onboarding, inbox, and Settings screens.

```text
+------------------------------------------------------------------+
| triage-mail          draggable empty area             [−] [□] [×] |
+-----------------+------------------------------------------------+
| Sidebar         | Existing search toolbar                        |
|                 | Message list / reader                          |
+-----------------+------------------------------------------------+
```

Proposed baseline for Linux and Windows: approximately 40px height, app name on the
left, flexible drag region, and minimize/maximize-or-restore/close on the right.
Use `--toolbar`, `--text`, `--secondary`, and `--separator`; avoid a separate color
palette, decorative gradients, or new UI dependencies. Close has a distinct destructive
hover/pressed treatment. Controls have approximately 40px targets and visible keyboard focus.
The app name stays static: no subjects, addresses, or account metadata in the window title.
Search, sync status, account navigation, and Settings entry points retain their existing roles.

- `src/routes/+layout.svelte` currently renders route content without a global window shell.
- `InboxView` and `SettingsView` use `h-dvh`; `OnboardingView` uses `min-h-dvh`.

- `src-tauri/capabilities/main.json` grants `core:default` to `main`; window actions need

- The installed `@tauri-apps/api` exposes window dragging, minimize, maximize toggling,
  maximize-state reads, resize/focus listeners, and request-based close operations.
- `runtime.rs` cleans up authorization and subscriptions on window destruction.
  The title bar must preserve that lifecycle.
- Existing uncommitted onboarding/i18n work is outside this planning change and must be preserved.

## Behavior and boundaries proposed for approval

1. Mount one title bar in the root desktop shell, outside account/inbox screen switches.
   Use a full-height flex column with a fixed-height bar and a `min-height: 0` content area.
   Inbox and Settings fill the remaining height; onboarding scrolls inside that area.
   Preserve message virtualization, selection, and existing reader isolation.
2. Use an injectable, typed window adapter backed by the existing Tauri API. Detect native
   availability before accessing the current window. Browser preview renders content without
   desktop controls or a reserved title-bar gap; tests use a fake adapter.
3. Enable undecorated mode only together with working custom controls. Keep resizing enabled,
   retain current minimum dimensions, and verify resize edges, shadows, maximize/restore,
   multi-monitor movement, and display scaling in a native window.
4. Only the empty/title region initiates dragging with the primary pointer. Controls and
   content never initiate drag. Double-clicking that region toggles maximize exactly once;
   avoid combining independent native and DOM double-click handlers that both toggle.
   Native pointer behavior is a verification item, not something browser tests can establish.
5. Minimize delegates to the window manager. Maximize/restore icon and accessible name reflect
   actual native state, including changes through OS shortcuts. Subscribe once, reconcile after
   actions/resize, and clean up listeners, including registrations resolving after teardown.
   Focus changes may subtly mute the bar without reducing control readability.
6. Close requests the normal window close path; do not call destroy, force exit, or add
   minimize-to-tray behavior. OS close shortcuts keep working. Settings' proposed Stay/Discard
   guard governs dialog dismissal, not app exit; changing exit policy is a separate scope.
   Window controls remain available during pending forms and OAuth; native teardown owns cleanup.
7. Localize control names, tooltips, and fixed operation errors in EN/PT-BR. Support keyboard
   activation, hover/focus/pressed states, contrast preferences, and reduced motion. Handle
   rejected actions without unhandled promises, raw native errors, or false state changes.
8. Settings/palette overlays cover the application content below the title bar. Their focus
   traps and background-inert handling must exclude window chrome so window actions remain
   usable; verify this with bits-ui rather than assuming sibling placement alone is sufficient.
   Escape dismisses the applicable dialog; it never closes the window.
9. Restrict added capabilities to the main local webview and the necessary window operations
   and event access. No broad window-management permissions, remote origins, new domain IPC,
   storage changes, network calls, plugins, or Rust core changes.

## Platform scope and compatibility gate

Linux is the primary native acceptance environment. Validate undecorated behavior on the
available display backend and record whether it is X11 or Wayland. An unavailable backend
remains explicitly unverified. Do not promise Windows Snap Layout hover menus or identical
window-manager decorations; basic dragging, resize, snapping where available, and controls
need native evidence per platform.

Before applying shared undecorated configuration, confirm Windows/macOS coverage. Proposed
macOS treatment preserves native traffic lights in an integrated title region, using a
platform-specific configuration if supported by the installed Tauri version. Do not remove
native controls on an unverified platform: retain native decorations there and suppress the
custom bar until its path is verified. Linux-only verification must not be reported as full
cross-platform support. No new platform dependency or private OS API is pre-approved.
